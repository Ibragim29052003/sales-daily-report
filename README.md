# sales-daily-report

Скрипт строит по выгрузке заказов интернет-магазина отчёт `daily_by_sku.csv`: одна строка на пару «артикул - день».

| Колонка | Что в ней |
|---|---|
| `sku` | Артикул |
| `order_date` | День, ГГГГ-ММ-ДД |
| `orders` | Число заказов за день, отменённые тоже считаются |
| `revenue` | Сумма `quantity × price` только по выкупленным (`delivered`) заказам, ₽ |

Строки отсортированы по `sku`, затем по дате. Если у артикула в какой-то день не было ни одного заказа, строки за этот день нет.

## Как запустить

Нужен Python 3.10 или новее. Скрипт использует только стандартную библиотеку, ставить ничего не нужно.

```bash
git clone https://github.com/Ibragim29052003/sales-daily-report.git
cd sales-daily-report
```

Положите выгрузку в корень репозитория под именем `sales.csv` и запустите:

```bash
python3 daily_by_sku.py
```

Результат появится в `daily_by_sku.csv` рядом со скриптом. Пути можно передать явно:

```bash
python3 daily_by_sku.py path/to/sales.csv -o path/to/daily_by_sku.csv
```

В консоль выводится сводка, например `13798 orders (60 duplicate rows skipped) -> 631 rows in daily_by_sku.csv`. Если в выгрузке встретится строка, которую нельзя однозначно разобрать, скрипт остановится с кодом 1 и укажет номер строки файла, например `sales.csv:42: unknown status 'returned'`. Отчёт в этом случае не пишется.

Готовый отчёт по присланной выгрузке уже лежит в репозитории: [`daily_by_sku.csv`](daily_by_sku.csv). Сама выгрузка в репозиторий не включена.

## Как проверяли, что расчёт верный

1. **Независимый пересчёт на SQL.** [`checks/crosscheck.py`](checks/crosscheck.py) загружает сырую выгрузку в sqlite и заново считает отчёт запросом `GROUP BY`. Код скрипта при этом не используется, очистка данных написана отдельно на SQL. Затем результат сравнивается с `daily_by_sku.csv` построчно, с учётом порядка строк. На присланной выгрузке:

   | Показатель | SQL | Отчёт |
   |---|---|---|
   | Строк в отчёте | 631 | 631 |
   | Сумма `orders` | 13 798 | 13 798 |
   | Сумма `revenue`, ₽ | 10 276 540 | 10 276 540 |

   Расхождений нет. Чтобы убедиться, что сверка вообще способна найти ошибку, испортил одно значение `revenue` в копии отчёта: сверка упала и показала эту строку.

2. **Ручной пересчёт одной строки.** Взял `UYT-0010` за 07.09.2026: в выгрузке 6 строк, заказ `1010715` встречается дважды, значит заказов 5. Выкуплены три заказа: 2 × 890 + 890 + 890 = 3 560 ₽, два отменённых в выручку не входят. В отчёте `UYT-0010,2026-09-07,5,3560`, совпадает.

   ```bash
   grep ',2026-09-07,UYT-0010,' sales.csv
   ```

3. **Контрольные цифры.** В выгрузке 13 858 строк, из них 60 дублей, значит уникальных заказов 13 798. Ровно столько же даёт сумма `orders` по отчёту, то есть ни один заказ не потерян и не посчитан дважды. В отчёте 12 артикулов за 56 дней (17.08–11.10.2026). В 5 строках `revenue = 0`: в эти дни у артикула были только отмены, и строки остались в отчёте, потому что `orders` считает и отменённые заказы.

4. **Unit-тесты** (`tests/`, 27 штук): нормализация статусов, битые значения, пустое количество, дубли и противоречивые дубли, отменённые заказы в `orders` без выручки, сортировка, запуск CLI на маленькой «грязной» выгрузке. Чтобы проверить сами тесты, скрипт нарочно ломали пятью способами: выручка с отменённых, без удаления дублей, без приведения регистра, неверная сортировка, без `canceled`. Каждую поломку поймал хотя бы один тест.

5. **CI** на GitHub Actions прогоняет линтер и тесты на Python 3.10 и 3.14 при каждом push и pull request.

## Проблемы в данных и что с ними сделано

| Проблема | Сколько | Решение |
|---|---|---|
| Полные дубли строк | 60 заказов встречаются дважды | Заказ считается один раз (по `order_id`). Если бы строки одного заказа различались, скрипт остановился бы: непонятно, какая из них верная. В присланной выгрузке все дубли полностью совпадают |
| Статус в разном регистре и с пробелом: `Delivered`, `DELIVERED`, `Cancelled`, `CANCELLED`, `delivered␣` | 32 строки | Обрезаем пробелы и приводим к нижнему регистру |
| Статус `canceled` (американское написание) | 3 строки | Считаем как `cancelled` |
| Пустой `quantity` | 4 строки, все отменённые | В `orders` считаются, на выручку не влияют, поэтому количество не нужно. Пустое количество у выкупленного заказа было бы ошибкой |

Любой другой неизвестный статус, неверная дата, нечисловая или отрицательная цена или количество, пустой `order_id` или `sku` останавливают скрипт с номером строки. Молча пропускать такие строки опасно: отчёт выглядел бы правдоподобно, но цифры были бы неверными.

`order_id`, даты, артикулы и цены проверены: битых значений нет, у каждого артикула одна цена за весь период.

Сам я выбирал стек и подход (Python без зависимостей, ветки и PR), принимал решения по спорным данным, ревьюил и мержил каждый PR. Готовое решение прогнал по шагам у себя и вручную пересчитал контрольную строку (см. «Как проверяли»).

Что пришлось поправить или перепроверить за ассистентом:

- **Подсчёт проблем в данных.** Сначала ассистент насчитал 21 «грязный» статус вместо 32: не учёл 11 строк с пробелом в конце. При повторной проверке цифра исправлена.
- **Ложно пройденная проверка.** Сверку проверяли на копии отчёта с испорченным значением, и в первый раз она прошла. Оказалось, что `csv` в Python по умолчанию пишет концы строк `\r\n`, и подмена через `sed` просто не сработала. После исправления сверка падает как положено, а отчёт теперь пишется с `\n` (коммит `fix: write report with LF line endings`).
- **Пустой `quantity`.** Ассистент предлагал вынести его в «не уверен» и уточнить у рекрутера. Я усомнился, что это нужно. По условию («включая отменённые», «что с ними делать — решаете вы») ответ следует из задания, поэтому решение описано как допущение.
- **Комментарии в коде.** Изначально были на английском, попросил переписать на русском.

## Допущения и ограничения

Всё, что можно было трактовать по-разному, решено так:

- **Пустой `quantity` у отменённых заказов.** Заказ существует и отменён, а по условию отменённые входят в `orders`, поэтому он учтён. Количество нужно только для выручки, которой у отменённого заказа нет.
- **`canceled` — это `cancelled`.** Опечатка в написании. Любой другой неизвестный статус останавливает скрипт, а не трактуется на догадках.
- **Дубль определяется по `order_id`.** В выгрузке у каждого заказа один артикул. Если у одного `order_id` встретятся разные строки (например, два артикула), скрипт остановится с `conflicting rows`, а не посчитает молча неправильно.
- **Дни без заказов в отчёт не попадают.** Отчёт строится по фактическим заказам, нулевые строки не добавляются.
- **Цены и количества — целые числа.** Так в условии и в данных. Цена с копейками остановит скрипт, а не будет округлена.

Недоделанного нет.
